# Reference study - how 2026-era operator tools solve the five named defects

Scope note on sourcing: three kinds of source appear below.

1. **Primary, first-party** - a vendor's own docs/blog/changelog (Linear's own "How we redesigned the Linear UI," Vercel's Geist docs, Attio's help center, Notion Calendar's changelog, FullCalendar's own docs).
2. **Third-party CSS extraction** - tools that scrape a live marketing site's computed styles and republish them as a token table (`styles.refero.design`, the VoltAgent `awesome-design-md` corpus, `oh-my-design.kr`). These read real computed CSS off the live site, but they are unofficial, sampled from the **marketing site**, not the authenticated app, and can disagree with each other. Flagged per-value below.
3. **Teardown / analyst commentary** - third-party write-ups describing product behavior without exposing raw values.

Where two sources conflicted (Linear's accent color - see §3), I report the conflict rather than picking one silently, and I default to the value corroborated by outside knowledge/multiple sources. Where no value could be found or verified, it is marked **unverified** rather than invented.

## 1. Elevation without shadows

**The defect:** chip, card and pane are all `#1F1F1F` on `#1F1F1F`, separated only by a border. That is the 2013 tell.

**Move 1 - Linear: elevation is a lightness ladder, not a shadow stack.**
Linear rebuilt its theme engine in LCH color space specifically so elevation levels ("background, foreground, panels, dialogs, modals") could be generated as a consistent lightness progression rather than hand-picked shadows: *"different elevations for our surfaces... contrast of the content has also been improved by making our text and neutral icons darker in light mode and lighter in dark mode."* Third-party CSS extraction of the live marketing site (two independent tools, broadly agreeing) shows a 3-4 step surface ladder: Void/Canvas `#08090a`–`#010102` (page) → Surface-1 `#0f1011` (card) → Surface-2 `#141516`/`#161718` (hovered/elevated card) → Surface-3/4 `#18191a`/`#191a1b` (dropdown/deepest lifted surface) - each step roughly 3-5 points of L* lighter than the last, no shadow used at any step. Hairline borders exist but are a secondary signal (`#23252a` default, `#34343a`/`#383b3f` "strong," used for focus and nested-surface edges), not the primary depth cue.
Source: [How we redesigned the Linear UI (part II)](https://linear.app/now/how-we-redesigned-the-linear-ui) (primary); token table cross-referenced from [styles.refero.design/Linear](https://styles.refero.design/style/90ce5883-bb24-4466-93f7-801cd617b0d1) and [VoltAgent awesome-design-md/linear.app](https://raw.githubusercontent.com/VoltAgent/awesome-design-md/main/design-md/linear.app/DESIGN.md) (third-party extraction, marketing site).
Transfer: direct. This app already has `--surface1-3` tokens; the fix is making each step a distinct, slightly-lighter value and never reusing one step for both a chip and its parent, not inventing shadows.

**Move 2 - Vercel Geist: named elevation tiers with a fixed radius per tier, shadow reserved for what floats.**
Geist's own materials doc defines two families of elevation, each with its own radius: on-page surfaces (`material-base`/`material-small` = 6px radius, "everyday use / slightly raised"; `material-medium`/`material-large` = 12px radius, "further raised") and floating/overlay materials (`material-tooltip` 6px "lightest shadow" → `material-menu`/`material-modal` 12px "lift from page / further lift" → `material-fullscreen` 16px "biggest lift"). The explicit design rule: *"nesting multiple elevated materials should be avoided unless the interaction genuinely requires layered floating UI"* and *"heavy decorative shadows should be avoided, since elevation is meant to clarify layering rather than create a floating-card aesthetic."* Independent teardown analysis of the same system describes it as "border-first": most static elements are a 1px border; shadow is reserved for things that must appear *above* the page plane (menus, modals, popovers), not for cards sitting flat on the page.
Source: [vercel.com/geist/materials](https://vercel.com/geist/materials) (primary, published token names/radii); shadow-philosophy characterization corroborated by third-party design-system breakdown [designsystems.one/vercel-geist](https://www.designsystems.one/design-systems/vercel-geist) (analyst commentary, radii independently confirmed against the primary doc).
Transfer: direct, and this is the cleanest answer to "when do we use no boundary at all" - Geist's rule is literally: static/on-page content gets a border or nothing, shadow is reserved exclusively for content that overlaps other content (the calendar's hover popover, the command palette, a confirm dialog). A card sitting in a lane never gets a shadow under this rule.

**Move 3 - Raycast: depth via hairline + inset highlight ("keycap" treatment), never an outer drop shadow on static cards.**
Raycast's own design guidance for extension surfaces states plainly not to add drop-shadows to cards/panels; depth comes from an "inset key shadow stack" instead. Third-party CSS extraction of the live app/marketing surfaces shows the mechanism concretely: a card's "shadow" is actually two 1px insets stacked - an outer `rgb(27,28,30) 0 0 0 1px` (the border, as a shadow so it can composite with the inset) plus an inner `rgb(7,8,10) 0 0 0 1px` (a one-pixel dark inset that reads as a recessed lip). A pressed/active button adds a third layer, a 1px white-alpha inset top edge (`rgba(255,255,255,0.05) 0 1px 0 0`) simulating a highlight catching light from above, paired with a 1px dark inset at the bottom. Card containment borders sit at `rgba(255,255,255,0.06)`, input borders slightly stronger at `rgba(255,255,255,0.08)` - both barely-there alphas, not solid grey lines.
Source: design-guideline characterization drawn from Raycast's own developer docs corpus (fetched via [developers.raycast.com/llms-full.txt](https://developers.raycast.com/llms-full.txt), primary but this specific "don't add drop-shadows" quote could not be re-isolated in the current doc tree - treat that one line as **unverified**, sourced only via secondary summary); token values from third-party extraction [oh-my-design.kr/design-systems/raycast](https://oh-my-design.kr/design-systems/raycast) (marketing-site scrape, unofficial).
Transfer: partial. The specific inset-highlight-as-"keycap" treatment is a strong, cheap move for buttons and chips (an interior 1px light-alpha top edge instead of a border makes a flat block read as physically raised without any drop shadow bleeding onto the green frame). The multi-layer glow/ring treatments Raycast uses for hero/marketing cards do **not** transfer - those are built for pure-black canvases and would look muddy against the app's `#1F1F1F` surfaces and the lime/pistachio frame; skip those layers.

**Move 4 - when to use no boundary at all: Vercel's explicit rule, Linear's practical default.**
Geist's stated principle - border for structure, shadow only for overlap, avoid stacking materials - implies a fourth state: **nothing**. A chip resting on a surface one step lighter than its parent needs neither border nor shadow if the lightness step itself is legible (a ≥3-4% L* jump reads as a boundary to the eye without drawing one). This is the option this app currently skips entirely - every depth relationship is expressed as a border because no lightness step exists to do the job instead.
Source: same as Move 2, [vercel.com/geist/materials](https://vercel.com/geist/materials).
Transfer: direct, and this is the highest-leverage single idea in this section - it is the answer to "kill same-colour-on-same-colour," not a shadow, a **lightness step**.

## 2. Control design and button hierarchy

**The defect:** Edit / Schedule / Regenerate / Add image / Delete render as five identical grey rectangles; only Delete (red) has any signal.

**Move 1 - Geist: five named variants (Default/Secondary/Tertiary/Error/Warning) mapped to three sizes, with an explicit labeling rule for destructive actions.**
Geist's Button component ships five variants - Default (primary), Secondary, Tertiary, Error, Warning - at three sizes (small/medium/large, plus a "tiny" size reserved for icon-only) and a hard accessibility rule for icon-only buttons: the `aria-label` must name **the action and the target** ("Copy deployment URL"), never the icon alone ("Copy"). Destructive actions use the Error variant with a mandated label pattern of **Verb + Noun** ("Delete Project," never a bare "Delete"), and Geist's best-practice guidance is explicit that `Button` is reserved for state-mutating actions (deploy, save, delete) - implying lower-stakes actions (view, copy, dismiss) belong in a lighter component, not a full button.
Source: [vercel.com/geist/button](https://vercel.com/geist/button) (primary).
Transfer: direct and close to a template. Map this app's five actions: Edit and Schedule are state-mutating → Secondary weight (not Default - Default/primary is reserved elsewhere, see §3). Regenerate is also state-mutating but riskier/rarer → Tertiary or a confirm-gated Secondary. Add image is additive/low-stakes → Tertiary, possibly icon-only with a real aria-label. Delete → Error variant, labeled "Delete draft," not floating alone as the only colored thing in a grey row.

**Move 2 - Linear: three-tier weight system (Primary/Secondary/Tertiary) with fixed padding and radius per tier, primary color reserved for exactly one action.**
Cross-referenced third-party CSS extraction of Linear's live button styles gives concrete, consistent numbers across two independent scrapers: Secondary buttons use the surface-1 background, ink text, a 1px hairline border, ~8px 14px padding, and a 6-8px radius; Tertiary buttons drop the border and background entirely (canvas-colored, text-only, same padding); Primary buttons are the only ones that carry the brand accent as a *fill*. Padding and radius are identical across tiers - **only fill and border change**, which is what makes the row still read as one family rather than three unrelated components.
Source: [styles.refero.design/Linear](https://styles.refero.design/style/90ce5883-bb24-4466-93f7-801cd617b0d1) and [VoltAgent/linear.app DESIGN.md](https://raw.githubusercontent.com/VoltAgent/awesome-design-md/main/design-md/linear.app/DESIGN.md) - both third-party extractions of the marketing site, values broadly agree with each other on padding/radius (8-14/6-8px), so treated as reasonably reliable; **the accent hex itself conflicts between the two sources - see §3, do not reuse that specific number here.**
Transfer: direct. The padding-and-radius-constant, fill-and-border-variable pattern is exactly the fix for "five identical grey rectangles": keep every button the same shape, vary only what's inside it.

**Move 3 - general pattern (corroborated across multiple UI-pattern sources, not one named tool): icon-only is reserved for standardized, unambiguous, low-frequency actions; everything else keeps a label.**
The convergent guidance across button-pattern literature: icon-only buttons should be reserved for actions with a "strong, immediately recognizable visual attribute" (a pin, a trash can) and are explicitly discouraged for routine or ambiguous actions because "users generally learn correct interpretations better with text than icons alone." Tertiary/quiet actions are additionally kept physically separated from primary/secondary clusters specifically to avoid accidental selection next to a destructive or committing action.
Source: pattern synthesis via [Eleken button UI guide](https://www.eleken.co/blog-posts/button-ui-design) and [Carbon Design System button usage](https://carbondesignsystem.com/components/button/usage/) (both are published design-system/pattern-library docs, not one of the five named 2026 tools - cited as corroborating pattern literature, not as a primary "how tool X does it" source).
Transfer: direct as a placement rule - "Add image" is a plausible icon-only candidate (a recognizable glyph, low stakes); "Regenerate" and "Delete" are not (their consequence is high, so they should keep text and sit apart from the low-stakes cluster, not inline with it).

**Move 4 - action-row placement: put the row where its target lives, not floating below a large empty field.**
Linear's own documentation of its issue sidebar shows action affordances living directly in-line with the property they act on (the assignee field itself is the click target, not a separate "Change assignee" button elsewhere on the screen) and Geist's guidance frames buttons as things that "mutate state" attached to the state they mutate. Neither tool floats a control row disconnected from its content in a large empty field - the control sits adjacent to (or overlapping, on hover) the object it changes.
Source: [linear.app/docs/assigning-issues](https://linear.app/docs/assigning-issues) and [linear.app/docs/labels](https://linear.app/docs/labels) (primary docs); [vercel.com/geist/button](https://vercel.com/geist/button) best-practices section (primary).
Transfer: direct - the draft window's action row should sit at the bottom edge of the 640px LinkedIn artifact it acts on, not spanning the full ~1250px column with dead space below it (this is also the fix named in defect #6 of the brief).

## 3. Accent budget

**The defect:** lime is spent full-width on "Post note," one of the least important actions on the screen.

**Move 1 - Linear: the accent is explicitly reserved for exactly one action per view, never for decoration or secondary buttons.**
Both third-party extractions of Linear's marketing site agree on the *rule*, even though they disagree on the exact hex (one reports an "Acid Lime `#e4f222`," described as *"reserved exclusively for the single primary action per view - never for decoration, never for secondary buttons"*; the other reports a lavender-blue `#5e6ad2` as "Primary," used for "brand mark, focus rings, primary CTA"). The lavender-blue value matches Linear's long-established, widely-documented brand color from outside sources, so the lime claim from the first scraper is treated here as **likely a scraping error** (possibly a sampled demo/theme page) and is **not used as a value** - only the *discipline* it independently confirms is used: one accent, one action, per screen.
Source: conflict between [styles.refero.design/Linear](https://styles.refero.design/style/90ce5883-bb24-4466-93f7-801cd617b0d1) (reports `#e4f222`) and [VoltAgent/linear.app DESIGN.md](https://raw.githubusercontent.com/VoltAgent/awesome-design-md/main/design-md/linear.app/DESIGN.md) (reports `#5e6ad2`) - flagged, not resolved to a specific hex here; **the rule, not the color, is the citable move.**
Transfer: direct - this is the single most important rule for defect #4. "Post note" does not get lime. Whatever action on this screen is the one the operator is actually there to do (ship the draft, approve, send) gets it instead, and it appears once.

**Move 2 - Raycast: color is rationed to roughly 2% of visual surface; the brand red is confined to specific, named surfaces, and blue (not red) does the everyday interactive-accent work.**
Independent analysis of Raycast's public surfaces states the palette is "98% achromatic" - the brand red (`#FF6363`) is confined to the logo, hero artwork, an AI badge, and one diagonal stripe motif, and explicitly does *not* double as the interactive accent. That job - links, focus states, selected list items - goes to a separate blue (`hsl(202,100%,67%)` / roughly `#55b3ff`), applied at low-alpha as a *tint* on interactive surfaces (`hsla(202,100%,67%,0.15)`) rather than a solid fill outside of the primary button itself.
Source: [oh-my-design.kr/design-systems/raycast](https://oh-my-design.kr/design-systems/raycast) (third-party extraction, marketing site) - the specific "98% achromatic" framing traced to the same synthesis and is analyst commentary, not a raw measured value; treat the ratio as directionally indicative, not a precise measurement.
Transfer: direct in spirit, partial in detail. This app has one accent (lime), not two, so it cannot split brand-color from interactive-color the way Raycast does with red/blue. The transferable idea is the **low-alpha tint for "selected/active but not primary"** states - e.g. a selected calendar cell or an active filter chip gets a lime-tinted background at ~10-15% alpha, not a full lime fill, keeping the full-strength fill reserved for the one primary action.

**Move 3 - what carries emphasis when the accent is not available: weight, position, and size - never a second color.**
Geist's variant system (Move 2, §2) demonstrates this directly: Secondary and Tertiary buttons carry no color at all - hierarchy below the single accent-filled Default button is expressed purely through fill-vs-no-fill and border-vs-no-border, at identical size and radius. Nothing "competes" with the accent by introducing a second saturated color; competition for attention is resolved with position (primary action first/rightmost in a row) and weight (filled vs. outlined vs. text-only), not hue.
Source: [vercel.com/geist/button](https://vercel.com/geist/button) (primary).
Transfer: direct. Today this app's non-lime buttons are already colorless (grey), which is correct - the failure is that lime is spent on the wrong one, not that too many things are colored. Fixing the budget is a re-assignment problem, not a de-saturation problem.

## 4. Information design for label/value pairs

**The defect:** ALL-CAPS label + value stacked inside a bordered box, repeated everywhere - reads as a database inspector.

**Move 1 - Linear: property fields are inline, unboxed, and keyboard-addressable; the field itself is the click target.**
Linear's own docs describe every sidebar property (assignee, priority, label, status) as directly editable in place: *"apply labels to any issue with the shortcut L, or by clicking into the label property field in an issue's right sidebar."* There is no separate "edit" affordance and no bordered container described anywhere in the docs - the value's own text is the button, and a single keyboard shortcut (S for status, P for priority, L for labels, A for assignee) is the alternate path to the same field. Nothing in Linear's documented interaction model wraps a property in a box; the row is the unit, not a bordered card containing a label-over-value pair.
Source: [linear.app/docs/labels](https://linear.app/docs/labels), [linear.app/docs/priority](https://linear.app/docs/priority), [linear.app/docs/assigning-issues](https://linear.app/docs/assigning-issues) (all primary).
Transfer: direct - this is close to a template fix for defect #5. Drop the border entirely; make the value itself the interactive/editable surface; keep the label as a quiet inline prefix, not a stacked all-caps header.

**Move 2 - Linear (cards): when a property list would overflow, don't show all of it - show the highest-priority subset and let a hover-and-peek reveal the rest, rather than compressing everything into visible boxes.**
Linear's own account of its board-card design: *"descriptions are not shown on cards, and if an issue has many properties, not all may fit - users can hover and press Space to peek at more detail, or open the full issue to see all properties."* This is an explicit density decision: rather than shrinking every property to fit, the system chooses a fixed small set for the compact view and defers the rest to an on-demand reveal.
Source: [How we redesigned the Linear UI (part II)](https://linear.app/now/how-we-redesigned-the-linear-ui) synthesis, corroborated by [linear.app/docs/board-layout](https://linear.app/docs/board-layout) (primary).
Transfer: direct for any dense metadata block (QA, Source, Log, Fields rows named in the brief) - pick the 2-3 facts that matter at rest, defer the rest to expand/hover, instead of shrinking every field to fit inside a box.

**Move 3 - Attio: the record panel is resizable, has a "view all values" progressive-disclosure step, and edits happen via direct interaction with the value (drag to reorder, right-click for history) - no indication anywhere in Attio's own docs of a bordered label-over-value block.**
Attio's help center describes the record details panel as attribute rows the user can resize (drag the panel divider), expand ("Clicking 'View all values' expands the full list of attributes"), search within ("Search attributes"), and directly manipulate - multi-value fields like email addresses are reordered by "dragging the handles," and edit provenance is inspected via right-click → "View edit history" directly on the value, not via a separate audit panel. This describes a system where the value is a live, manipulable object, not a static string presented under a caption.
Source: [attio.com/help/reference/attio-101/attios-data-model/understanding-records](https://attio.com/help/reference/attio-101/attios-data-model/understanding-records) and [attio.com/help/academy/introduction/record-pages](https://attio.com/help/academy/introduction/record-pages) (both primary, help-center docs). Note: Attio's help docs describe *behavior*, not visual spec - no hex/px values were found for label typography, alignment, or spacing; treat the visual specifics (label size, weight, capitalization) as **unverified** for Attio specifically, only the interaction model is confirmed.
Transfer: direct for the interaction model (click-through history, drag-to-reorder, progressive "view all"); the exact visual treatment is not verifiable from Attio's public docs, so pattern this app's typography off the confirmed Linear values instead (Move 1) and use Attio only for the "how a field becomes a live object" idea.

## 5. Calendar / time-grid chips

**The defect:** an 87px chip in a 124px cell (70% of cell height), reads as a raised button, cannot show two posts in one day; tooltip pins to the viewport corner instead of the cell.

**Move 1 - Amie: depth on a chip comes from a barely-there shadow (4-12% opacity) plus a hue difference between chips, never a border, and never more than roughly a tenth of the surface's usual shadow strength.**
Independent design-teardown coverage of Amie states its shadows sit at "4-12% opacity instead of the typical 10-20%," explicitly framed as: *"elevation through 4% and 12% opacity shadows is almost invisible by design - cards feel like they float through color differences, not shadow theatrics."* Amie's other defining move is a 15-step, ~135-token color system used specifically so a day's events are told apart **by hue**, not by size or boldness - a user is meant to recognize the "shape" of a day by its colors before reading any text.
Source: [blakecrosley.com/guides/design/amie](https://blakecrosley.com/guides/design/amie) (design-analysis writeup, third-party - the 4-12% figure is this author's measurement/estimate, not a value published by Amie itself; treat as **directionally credible, not verified against Amie's own source**).
Transfer: partial. The near-invisible shadow idea transfers (a chip should not look bevelled/pressed); Amie's 15-color hue system does not transfer to a single-accent (lime) system with a fixed pistachio frame - this app should differentiate calendar chips by a state/type indicator (a rail, a dot, a label glyph) at fixed small size, not by rotating through many hues, since the brand identity is explicitly locked to one accent.

**Move 2 - Vercel Geist + FullCalendar convention (mechanism, not one branded tool): fixed-height chip rows, a hard cap on visible chips per cell, and any excess collapses into a single "+N" affordance that opens a popover - never a taller chip.**
FullCalendar's own documented options (`dayMaxEvents` and `dayMaxEventRows`) formalize the industry-standard mechanic directly: cap the number of event rows a cell will render, and once the cap is hit, "the rest will show up in a popover" behind a "+more" link - chip height is never the variable that flexes to fit more content, row *count* is. This is the same mechanism Notion Calendar ships in its own changelog ("fixes blocked event chips... not being merged"), confirming multiple events collapsing/merging into a single rendered unit is treated as correct, expected behavior worth shipping bug fixes for, not an edge case to avoid.
Source: [fullcalendar.io/docs/event-popover](https://fullcalendar.io/docs/event-popover) (primary docs for the mechanism); [cron.com/changelog](https://www.cron.com/changelog) (Notion Calendar/Cron's own changelog, primary, confirms the merge behavior exists and is actively maintained - exact pixel/row numbers for Notion Calendar's own cap were **not found and are unverified**).
Transfer: direct - this is the fix for defect #8 (87px chip in a 124px cell). Chip height should be fixed and small (enough for one line of text plus a state indicator), the cell should cap at N visible chips (2 is enough at this cell size), and anything beyond that collapses into a "+1" that opens a popover - never grows the chip.

**Move 3 - Google Calendar (2026 Material redesign): chips get rounder and denser, not taller - state moves into the chip's own fill/icon, not its size.**
APK teardown coverage of Google Calendar's Material 3 Expressive redesign describes chips becoming visually rounder and gaining an icon/label baked into the chip itself (task vs. event vs. birthday distinguished by an icon inside the chip, not by chip height or extra chrome), alongside a separate, more consequential move: Google expanded per-event color choice from an 11-color cap to a 200-shade picker, explicitly to let *state/category* live entirely in color+icon rather than in size.
Source: [androidpolice.com Material 3 Expressive teardown](https://www.androidpolice.com/android-16-material-3-expressive-on-google-calendar/) (APK teardown, third-party, describes an in-progress/beta redesign - treat feature specifics as **directionally accurate but not final-shipped-spec verified**); color-picker expansion confirmed via Google's own [Workspace Updates blog post](https://workspaceupdates.googleblog.com/2026/06/custom-event-colors-in-google-calendar.html) (primary).
Transfer: partial. Rounder + icon-in-chip transfers directly (communicate state via a small glyph/dot inside the fixed-size chip, not via extra height). The 200-color picker does not transfer - this app has one accent and a locked palette; state should be communicated with a small fixed vocabulary (2-4 states: scheduled / posted / drifted / failed) via icon or a short label fragment, not color proliferation.

**Move 4 - popover anchored to the triggering cell, not the viewport: confirmed as the expected norm by user complaints when other tools get it wrong, not by an app explicitly documenting its own algorithm.**
No named 2026 tool publishes its exact popover-positioning algorithm publicly (this is implementation detail, not marketing/docs content, across every tool checked). The norm itself is well established by omission: FullCalendar's own popover is, by design, triggered by and visually tied to the "+more" link inside the specific day cell (not a global viewport position), and a Zoho Calendar user-forum complaint independently confirms the expected behavior by describing its absence as a bug: *"after adjusting height/width, the pop-up always appears in the center-mid of the calendar, no matter how big the calendar is"* - cited by the reporting user as a defect precisely because cell-anchored positioning is the assumed correct behavior.
Source: [fullcalendar.io/docs/event-popover](https://fullcalendar.io/docs/event-popover) (primary, confirms the popover is cell-triggered); [Zoho Calendar community forum](https://help.zoho.com/portal/pt/community/topic/pop-up-windows-are-positioned-wrong-can-i-control?page=24) (user complaint, third-party, illustrative of the norm by contrast - not a spec).
Transfer: direct as a requirement, **unverified as a specific algorithm** - the concrete fix (defect #9, tooltip pinned to viewport top-left) is to anchor the popover to the triggering chip/cell's bounding rect (e.g. with a floating-UI/anchor-positioning library), which is standard practice, not a specific number to cite.

## What would make this app read as 2026

Ranked by leverage (impact on the "2013" verdict, relative to effort), each traceable to a cited move above.

1. **Replace every same-colour-on-same-colour boundary with a lightness step, not a border.** (§1 Move 1, Move 4 - Linear, Geist) Define 3-4 surface steps and make chip/card/pane each sit one step lighter than its parent; this alone kills the single tell Ivan named ("2013," "ugly 3d," "raised button").
2. **Re-spend the accent: one lime fill per screen, on the action that matters, never "Post note."** (§3 Move 1, Move 3 - Linear, Geist) Audit every current lime use, cut to one per screen; everything else stays grey/outlined.
3. **Build one button component with Default/Secondary/Tertiary/Error variants at fixed padding+radius, varying only fill/border.** (§2 Move 1, Move 2 - Geist, Linear) Fixes the five-identical-rectangles row directly: Edit/Schedule = Secondary, Regenerate = Tertiary or confirm-gated, Add image = Tertiary/icon-only, Delete = Error with a "Delete draft" label, not a bare red box.
4. **Kill the ALL-CAPS-label-in-a-box pattern; make the value itself the click target, label as a quiet inline prefix.** (§4 Move 1 - Linear) Removes the "database inspector" read from every metadata surface (QA, Source, Log, Fields, Ops, Settings) in one pattern change.
5. **Fix calendar chips: fixed small height, cap 2 visible per cell, overflow becomes a "+1" that opens a popover - never grow the chip.** (§5 Move 2 - FullCalendar mechanism, Notion Calendar changelog) Directly resolves the 87px-in-124px defect and the two-post-day problem.
6. **Anchor the calendar hover/tooltip to the triggering cell's bounding rect, not the viewport corner.** (§5 Move 4) Small fix, high annoyance-reduction; standard practice everywhere it was checked.
7. **Use an interior 1px light-alpha top inset (a "catches the light" edge) instead of a border for anything that should read as physically raised** - buttons in their default state, the primary action's fill. (§1 Move 3 - Raycast) Cheap, and it is the mechanism that makes a flat block read as tactile without a drop shadow that would bleed oddly against the green frame.
8. **Move the action row to sit against the content it acts on (bottom edge of the 640px artifact), not spanning the full column with dead space below.** (§2 Move 4 - Linear, Geist) Directly resolves defect #6 and reinforces the new button hierarchy by putting it in context rather than floating.

Everything reserved but not ranked in the top 8: Amie's near-invisible (4-12%) shadow opacity as a general "don't let anything look bevelled" ceiling (§5 Move 1); Attio's drag-to-reorder / right-click-for-history pattern for any multi-value field this app has (§4 Move 3); Superhuman's rule that every visible action should have a matching palette command, useful for the command-layer work elsewhere in this run but not one of the five named defects.
