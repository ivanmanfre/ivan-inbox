# SKEPTIC-CROSS-TENANT — verdict

All probes below run live, read-only (SELECT/HEAD/scoped POST to `claude-brain-query`), service key per `phase0-research-db.md` method (`claude-code-railway/main.py:46`). No writes.

## Claim-by-claim verdict

**1. Assembler's own broker-side queries (P15, B10, B4, B5, B9) are scoped in SQL above the limit, never post-fetch.**
CONFIRMED-SAFE, for the documented query shapes only. Reproduced the R2/P15 shape live: `client_id=in.(ivan,global,shared-tech)&file_path=eq.project/MEMORY.md&limit=1` → returns only `{client_id: ivan, updated_at: 2026-08-01T10:40:18Z}`. This is real code running server-side in the edge function (not model-issued), so it is an actual control, matching the spec's own claim that "the control is the SQL" for these blocks.
⚠ Caveat: I also ran the *identical* query with `client_id` dropped entirely (adversarial: what if a future edit to the assembler code regresses the filter, or the P15 point-read constant gets refactored wrong). Result with no client_id, `limit=1`: still returned `ivan` — **but only because of undefined natural row order, not an ORDER BY**. Ran the same unscoped query with `limit=5`: **both rows return, `ivan` first then `proswppp`** — confirming F4's own admission that "ivan wins today, by luck not by design" is literally true and reproducible. Postgres gives no ordering guarantee absent `ORDER BY`; a vacuum, index-only scan plan change, or replica promotion can silently flip which tenant's `project/MEMORY.md` a `limit=1` unscoped query returns. **This is a live, reproducible fragility**, not hypothetical — it just happens not to have flipped yet.

**2. F5 — one `in.()` query silently drops a whole tier (shared-tech) at the 1000-row PostgREST cap.**
CONFIRMED, reproduced live: `client_id=in.(ivan,global,shared-tech)&limit=2000` → 1000 rows, `{ivan: 972, global: 28}`, **zero shared-tech**. `limit=2000` is silently ignored server-side. The spec's mitigation (issue one query per tier, never one `in.()` page) is the only correct fix and is what the assembler is specified to do for its own injection blocks (§2 "one query each"). CONFIRMED-SAFE *if and only if* Phase 3 actually implements per-tier fetches — this is unverifiable against a spec document; it is a build-time discipline, not something the doc itself enforces.

**3. Depth recipes (R1–R5): is tenant scoping in the query, or purely advisory prose the model might ignore?**
REFUTED as a "safe" claim — it is **purely advisory prose with zero server-side enforcement**, and the spec is only half-honest about this. Reproduced live: `claude-brain-query mode:recall` with `query:"Derek CRM Pipedrive signal check"` and **no `client_ids`** → **5 of 5 results are `proswppp`** (worse than the spec's own 3-of-5 example). Same query **with** `client_ids:["ivan","global","shared-tech"]` → 5 of 5 `ivan`, clean. The only thing separating these two outcomes is text in a system prompt telling the model to always include the array. The container's own permission allowlist (`Bash(curl:*)` unprompted, per DEPTH-SPEC §3.2) means a model that drops the parameter — by confusion, by prompt injection from a hostile memory row using T4-style authority language, or simply by paraphrasing the recipe instead of copy-pasting it — gets an **immediate, silent, no-error cross-tenant read** using the service key that's already sitting in the container env. INJECTION-SAFETY.md T7 is candid about this exact gap for *writes* ("nothing technically prevents the row-write"); no document states the parallel, arguably more dangerous point for **reads**: the depth channel's tenant safety is 100% model-compliance-dependent and the failure mode is invisible (no error, no anomaly, just a wrong-tenant answer). This should be stated as plainly as T7 is.

**4. Graph modes (connections / neighbors / related_to) — is exclusion from the recipe total, and is the "cannot be scoped" claim true?**
CONFIRMED on both counts. (a) Grepped `claude-brain-query.v22.as-deployed.ts`: `connections` (line 218) and `related_to` (line 268) call their RPCs with **`p_client_ids: null`** hardcoded, ignoring any `client_ids` in the request body — confirmed by direct read of source, lines 229 and 278. `neighbors` (line 241) doesn't even accept the parameter: `.from('claude_memory').select('id').eq('file_path', file_path).order('updated_at', {ascending:false}).limit(1)` — zero client filter of any kind. (b) Live-probed `neighbors` on the collision path `project/MEMORY.md` **while passing `client_ids`** (to test whether the param is silently accepted-but-ignored, per the spec's warning) → the param had no effect; result resolved via `updated_at` race, Ivan's row (2026-08-01) beating ProSWPPP's (2026-07-31) by one day, exactly as the spec predicted. (c) Confirmed by reading DEPTH-SPEC §4's five recipes verbatim: none of R1–R5 invoke `connections`, `neighbors`, or `related_to`. Total exclusion from the documented recipe set is real. But per point 3 above, "excluded from the recipe" is not "technically unreachable" — nothing stops a model from calling `mode:neighbors` directly with curl; the spec itself concedes this ("cannot be made safe from here") which is honest, but the practical residual is identical in kind to point 3's gap and should be named in the same breath, not filed as a separate, lesser concern.

**5. `client_instances.compiled_context` — injected unframed every turn (F3/T9); is it at least tenant-scoped?**
CONFIRMED-SAFE for the specific query, UNPROVEN for the general guarantee. Live-probed `client_instances`: 6 rows, one per tenant, distinct `client_name` values (`Ivan System`, `ProSWPPP`, `Lemonade`, `The Reeder`, `SecondMile`, `Agency Ops`), no duplicates today (`Counter` all =1). The assembler's documented query `?client_name=eq.Ivan System&limit=1` (PARITY-SPEC §5, B5) returns exactly Ivan's 4,596-char `compiled_context` and nothing else — reproduced live. So *today* the query is clean. But this is the same shape of guarantee as the `project/MEMORY.md` file_path collision (F4): correctness rests on `client_name` staying unique, and I found no schema-level unique constraint confirmed anywhere in the research docs or via REST introspection (not checked at the Postgres catalog level — out of reach via REST-only probing). If a second `client_instances` row is ever created with `client_name = 'Ivan System'` (typo, migration, duplicate onboarding), the `eq.` filter with `limit=1` has the identical undefined-order hazard demonstrated in point 1. Separately and unconditionally: T9 stands as reproduced — this channel is live, unframed, and fires every turn regardless of anything this run builds; not this skeptic's fix to make, but the tenancy question ("is it scoped") gets a qualified yes with the same caveat as everywhere else in this spec: clean by current uniqueness, not by an enforced constraint.

## Required spec amendments

1. **PARITY-SPEC / DEPTH-SPEC**: state explicitly, next to F4, that unscoped `limit=1` reads on a colliding `file_path` (or a colliding `client_name`) are order-dependent and **not guaranteed** by Postgres absent `ORDER BY` — currently only demonstrated as "true today," not "true by design." Either add an explicit `ORDER BY` tie-break rule (e.g., prefer `client_id=eq.ivan` exact match, never rely on scan order) or accept and name the residual risk as such.
2. **DEPTH-SPEC**: add a threat-model row (T-series, alongside INJECTION-SAFETY's T7) stating plainly that the depth recipes' tenant scoping is **advisory-only, unenforced by any server-side gate**, that omitting `client_ids` produces an **immediate, silent, undetectable cross-tenant leak** (demonstrated: 5/5 proswppp rows for an innocuous query), and that this is a strictly worse failure mode than T7 because it requires no injected instruction at all — plain model error or paraphrase suffices.
3. **DEPTH-SPEC §5**: fold the graph-mode exclusion's "cannot be made safe from here" language into the same amendment as #2 — right now it reads as a narrower, mode-specific caveat when it is actually the general condition of the entire depth channel.
4. **PARITY-SPEC B5 / client_instances**: note the `client_name=eq.` uniqueness dependency alongside the `file_path` (F4) one, since it's the same class of accidental-not-structural safety.

Final verdict: the **broker-side assembler queries** (parity injection) are a real, code-enforced control and CONFIRMED-SAFE as specified, modulo the unscoped-order fragility above. The **depth recipes** are CONFIRMED-UNSAFE-BY-DESIGN in the sense that their only enforcement is prose the model is trusted to follow — proven exploitable in one query, no injection required — and the spec underclaims this residual relative to how candidly it treats the write-side (T7) equivalent.
